# ADR-0003: 挙動はキー列と期待する画面の組で定め、エンジンはアダプタ越しに測る

- Status: Proposed
- Date: 2026-11-06
- Deciders: kiyama
- Level: L2
- Phase: 3、5〜9
- Supersedes: なし

## Context

「同じ挙動」を言葉で決めると、実装ごとに解釈が分かれる。検査で決めるには、キーを打ったら何が見えるべきかを、データとして書く必要がある。

そのデータは、まだないエンジン (ADR-0004) にも、今あるエンジン (ddskk、libskk、skkeleton、cskk など) にも同じように当てられなければならない。エンジンごとに言語も呼び方も違う。

- libskk は C の関数で、キーを文字列でまとめて渡せる (`process_key_events`)。
- ddskk は Emacs の中で動き、表示は Emacs の buffer そのものである。
- skkeleton は Deno の中で動く。
- cskk は Rust で、C ABI を持つ。

正 (ADR-0002) の ddskk は、変換中の文字を buffer に直接書く。IME (libskk など) は、変換中の文字 (preedit) と確定した文字を分けて返し、使わなかったキーはアプリに任せる。この違いを吸収する決まりが要る。

## Decision

契約の本文は `conformance/SPEC.md` (英語) にある。要点は次のとおり。

- **検査項目** (case) は TOML で書く。1項目は、使う辞書と、いくつかの段 (step) からなる。各段は、キーの並びと、その後に見えるべき3つのもの (確定した文字列 `text`、変換中の文字列 `preedit`、入力モード `mode`) を持つ。段で書かなかったものは調べない。
- **キーの書き方**は、空白で区切った字句の並びにする。印字できる ASCII 1文字、`SPC`、`RET`、`BS`、`C-` と小文字 (例 `C-j`) だけを使う。Emacs の `kbd` に近い形なので、ddskk にそのまま渡しやすい。
- **preedit** は、ddskk が buffer に出す印 (▽、▼、送り仮名の前の `*`) を含めた1つの文字列にする。まだかなになっていないローマ字 (`▽かんj` の `j`) も preedit に含める。
- **観測と出力イベントの関係** (ADR-0009): 3つの観測は、エンジンの出力イベントの列を畳んだ値である。`text` は `Committed` の連結に、`NotHandled` になったキーをアプリの規則で当てたもの、`preedit` は最後の `Preedit`、`mode` は最後の `InputMode` である。検査項目は、出力イベントの列そのものは比べない。既存のエンジン (ddskk など) は私たちのイベントを出さないこと、同じ画面に至るイベントの列は1通りでないこと (preedit を2度出すなど) が理由である。キーの字句は、入力イベント `Key` の一部を書いたものである (`K` は `Char('K')`、`SPC` は `Space`、`C-j` は `Char('j')` と `ctrl`)。
- **アプリの役**はアダプタが演じる。カーソルが常に末尾にある1行の buffer を持ち、エンジンが使わなかったキーは決まった規則で buffer に反映する (文字は足す、`RET` は改行、`BS` は1字消す)。ddskk のように buffer を直接書き換えるエンジンも、preedit の外の文字を `text` として読む。
- **確認の問い** (ddskk が `X` で削除する前の yes/no) には、アダプタが yes と答える。検査項目にその答えのキーは書かない。
- **辞書**は、検査のために作った小さな合成の辞書 (`conformance/dict/`、UTF-8) だけを使う。ユーザーの辞書も公式辞書も使わない。各項目は、空のユーザー辞書か、指定した合成の辞書をユーザー辞書の初期値にして始まる。
- **アダプタ**は、標準入出力で1行1つの JSON をやりとりするプログラムにする。runner は1つの項目を丸ごと送り、アダプタは段ごとの観測を返す。合否は runner が決める。アダプタはどの言語で書いてもよい。
- **合格表**は、検査項目のファイルを行、エンジンを列にして、合格数/項目数を出す。
- 範囲は、ddskk マニュアルの基本の章 (5章) と、そこから参照される6章の節 (かなモードからカタカナ、全英文字の入力、暗黙の確定、誤った登録の削除) にする。v1 は 81 項目である。5章のうち、Emacs だけの機能 (インクリメンタル・サーチ、チュートリアル、オートフィル、カーソルを戻してからの `Q`) は外す。

## 決め方

実験とデータで決まる。ユーザーには聞かない。

手順:

1. 検査項目の検査 (カード C1)、runner (C2)、ddskk と libskk のアダプタ (C3〜) を作る。
2. 81 項目を ddskk で動かす。
3. ddskk で合わなかった項目は、ddskk の動きを確かめ、期待値を直すか、形式の欠けとして記録する。
4. libskk ともう1つのエンジンで動かす。

判定の基準:

- ddskk で全項目が合格する。合格しない項目は、理由を書いて形式の欠けとして扱い、形式を直す (版を上げる)。
- ddskk 以外の2つのエンジンで、アダプタが `error` や時間切れを返す項目が、全体の1割以下である。これより多いときは、形式がエンジンの差を吸収できていないので、形式を見直す。
- `make check` が、ネットワークもコンテナも使わずに、全項目の形を検査する。

## Options Considered

| 案 | 複雑さ | 費用 | 運用の手間 | 要点 |
|---|---|---|---|---|
| A. キー列と期待する画面の組をデータで書き、アダプタ越しに測る (推奨) | 中 | 中 | 低 | エンジンの言語に依らない。項目を足すのはデータを書くだけ |
| B. エンジンごとに単体試験を書く (cskk や libskk の試験の流儀) | 低 | 高 | 高 | エンジンの数だけ同じ試験を書き直す。比べられない |
| C. ddskk の画面を記録して、そのまま比べる (ゴールデンファイル) | 中 | 低 | 中 | 正解は機械で作れる。ただし Emacs の buffer の形が IME の preedit と合わず、比べる単位が決まらない |
| D. 状態機械の遷移表で定める | 高 | 高 | 中 | 厳密だが、エンジンの内部の状態に踏み込む。内部の作りが違うエンジンには当てられない |

## Trade-off Analysis

A は、外から見える3つ (確定した文字、変換中の文字、モード) だけを比べる。内部の作りが違うエンジンでも、同じ項目で測れる。B と D は内部に依存する。C は正解の作り方としては良いので、A の期待値を ddskk で確かめる手順として取り入れた。

捨てたもの:

- 候補の一覧の見た目。ddskk はエコーエリア、IME は候補の窓に出す。見た目は比べず、選んだ結果の `text` だけを見る。
- 辞書登録中の画面。ddskk は minibuffer に出し、libskk は preedit の中に出す。ddskk は minibuffer が入力を待つ間は外から読めない。そこで、登録を開くキーから閉じるキーまでを必ず1つの段に入れ、登録の後の `text` と学習の結果だけを見る。
- ユーザー辞書のファイルの中身。並び順や書き方はエンジンごとに違う。代わりに、同じ項目の中で「学習した候補が次は先に出る」ことを見る。ファイルの形は `jisyo` の検査が受け持つ。

## Consequences

- 楽になること: 新しいエンジンも、アダプタを1本書けば全項目で測れる。私たちのエンジンも、frontend (Neovim、fcitx5、TSF、Android) を通した形でも同じ項目で測れる。
- 難しくなること: ddskk のアダプタは、Emacs の minibuffer と確認の問いを扱う必要があり、作るのが一番難しい。
- 見直す条件: 学習を検査したくなったとき。私たちのエンジンは `Learn` を出し、既存のエンジンは前後のユーザー辞書を `jisyo` の diff にかければ同じ型の学習のイベントが得られるので、段ごとの観測に `learn` を足せる (版を上げる)。数値変換、注釈、補完、sticky shift、AZIK など、基本の章の外に広げるとき。設定 (profile) が必要になったとき (ADR-0002 の癖の一覧)。アダプタの約束を変えるときは `protocol` の版を上げる。
