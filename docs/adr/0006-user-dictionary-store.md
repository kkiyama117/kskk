# ADR-0006: 学習記録を個人サーバーで同期し、手元の記録で切断中も使う

- Status: Proposed
- Date: 2026-11-06
- Updated: 2026-11-12
- Deciders: kiyama
- Level: L2
- Phase: 2、4〜9
- Supersedes: なし

## Context

ユーザーは機械ごとに別の学習の辞書を持っている。fcitx5-skk は `user.dict` (EUC-JP)、skkeleton は `~/.skkeleton` (UTF-8)、CorvusSKK は `userdict.txt` (BOM 付き UTF-16LE) である (`docs/research/README.md`)。

どの実装も、メモリ上の辞書でファイル全体を書き直す (`docs/research/sync.md`)。共有フォルダで1つの辞書を使うと、互いの学習を上書きする。候補の和集合だけでは、削除を伝えられない。

この ADR は保存と同期の方針を提案する。記録の形式とまとめの規則は `skk-jisyo` が `jisyo/SPEC.md` に書く。既存の記録と純粋なまとめの処理を保ち、同期の手段を変える。

Cは中央サーバーを先に作り、peer-to-peerを後に足す選択肢(c)。skk-serverはmodule systemとし、学習同期と将来のskkserv形式検索を別moduleにする。開発はboiled。本番候補はVPSかTailscale上のPiで、最終選択は未決定である。

以下のwire形式、認証、確認応答などは設計提案であり、回答がその詳細まで承認したとは扱わない。この ADR は Proposed のままにする。Y0案は [server moduleと記録交換](../design/y0-server-modules-and-sync.md)に置く。

## Decision (提案)

1. **機械ごとの追記記録を保つ**。各機械は、自分の学習記録だけを生成して自分のログに追記する。ほかの機械の記録を受け取っても、その機械名で新しい学習を生成したり、既存の内容を書き換えたりしない。
2. **学習と記録の型を保つ**。候補の追加、先頭への移動、削除、注釈の変更を `LearnEvent` とし、機械 ID、連番、時刻を付けて `LogRecord` にする (ADR-0009、`jisyo/SPEC.md` の Learning events と Record)。削除も残す。今の辞書は記録から計算する。
3. **受信peerは記録の和集合を保持する**。最初は中央のskk-serverを使うが、交換規約は中央であることを前提にしない。記録の同一性は `(machine, seq)` とし、同一再送は1回、同じIDで内容が違えば `log-conflict` として拒む。client/serverの認証identityと、元のrecord.machineを区別し、中継でも内容を保つ。前後関係と候補の採否は既存のMerge規則で決め、到着時刻で変更しない。
4. **ローカルキャッシュは記録を保持する**。手元に、自分の追記ログと、最後に取得できたほかの機械の記録を残す。その全体から辞書を作る。自分のログは未送信記録の保管場所も兼ねる。接続できなくても、手元の辞書で入力し、自分のログに学習を続ける。まだ取得していない他機械の学習は、再接続するまで反映されない。
5. **接続時は不足した記録をpeerと交換する**。初期clientは自分の未送信記録を送り、他機械の不足分を取得する。将来のpeer間では、取得済みの他機械の記録も、元のIDと内容のまま中継できる。通信途中の切断やack喪失の後は再送できる。受信側の永続化前に送信済みと確定せず、確認位置はpeer別のhintに留める。downloadは機械ごとのcomplete prefixを組み立てて検証し、atomicにcacheを公開する。途中まで受信した行を完成したcacheとみなさず、既存recordを置換しない。own logの延長・復元をdownloadの権限に含めない。
6. **再接続後も、まとめは記録の和集合とする**。送信、取得、重複、切断の順序によらず、同じ記録集合になれば同じ辞書になる。候補の和集合ではなく、削除を含む記録の和集合である。ログは初期案では削除も圧縮もしない。長期切断した機械が戻ったときに削除済みの候補を復活させないため、削除記録を捨てる方式は別途設計する。
7. **通信を入力の中心から外す**。キー処理、学習、ローカル記録はサーバー応答を待たない。同期の通信と再試行は外側で行う。受け取った記録も、純粋な検証とまとめの処理に渡す (ADR-0009)。
8. **現在の IME への橋渡しを保つ**。CorvusSKK、fcitx5-skk、skkeleton には、まとめた辞書を各形式で書き出す。IME が変えたファイルを前回の書き出しと比較して学習に直す処理と、古い IME の上書きから削除が広がるのを防ぐ処理は変えない。各 IME に新しいサーバー通信を実装することは、この橋渡しの前提にしない。

### 同期の通信と skkserv を分ける

`yaskkserv2` のような個人サーバーを使うという希望を、既存の `yaskkserv2` が学習の同期を実装済みという意味には取らない。調査した skkserv の命令は検索と接続管理であり、学習を書き込めない (`docs/research/spec.md` の skkserv protocol、`docs/research/sync.md` の3節)。

skk-serverのhostが認証、listener、module registry、専用storageを管理し、syncを信頼済みの別componentとして読み込む。初期案はstatic registrationと設定enableであり、第三者pluginを自動実行するものではない。module systemは同一process内の設計境界で、悪意あるnative moduleのsandboxとは主張しない。lookupを後から追加しても、syncに検索を組み込まず、記録への権限を暗黙に継承させない。

Y0ではHTTP/TLSと相互認証、prefix hash、永続化後ack、切断時の再照合を提案する。wireとmoduleの詳細はY0文書を唯一の記述箇所とし、実装前にレビューする。同一機械のown logはADR-0009のhostが単独所有する。記録を外部の変換API、model provider、telemetryへ送る権限は含めない。

## 決め方

サーバーとキャッシュを使う方向は人の判断である。追記記録をキャッシュと未送信記録に兼用できるか、復帰後に収束するかは合成データで検証する。

判定の基準。既存の純粋な処理は `jisyo` の gate で、通信は今後の同期カードの gate で検査する。まだ検証済みという意味ではない。

- 2台分をどちらの順でまとめても同じ辞書のバイト列になる。3台分は6通りすべてで同じになる。
- 同じ記録を2度まとめても結果は変わらない。同じ `(machine, seq)` で異なる内容は衝突になる。
- `jisyo/SPEC.md` の Merge の順で、削除より古い追加を再取得しても候補は戻らない。削除より後の追加や先頭への移動では戻る。切断中の操作も、到着順でなくこの規則で比較する。
- 切断中に2台が追加、先頭への移動、削除を行い、復帰後に送受信の順を入れ替え、記録を再送しても、全記録を一度にまとめた辞書と一致する。
- サーバーが永続化した後で応答が失われても、再送で記録は増殖しない。取得中に切れても、次の取得で欠落を埋められる。
- サーバーが不通でも、取得済みの記録と自分の新しい学習を使える。未送信記録は再起動後も残り、復帰後に送れる。
- ログ末尾が書きかけでも、それより前の完全な記録を読める。部分的な末尾は報告し、自分のログへの追記を黙って続けない (`jisyo/SPEC.md` の Record)。
- IME が古い内容で上書きしても、渡したばかりの単語を削除として他機械へ広めない。取り込みと書き出しの既存の安全策を保つ。
- 各 IME 形式への書き出しを、合成データで読み戻せる。

### ユーザーに残る判断

中央先行・後からpeer-to-peer、module化、boiledでの開発は聞き直さない。実運用前に残るのは、VPS/Piの最終選択、認可deviceと管理者が辞書本文を読める範囲、署名/E2Eの必要性、鍵とbackupの管理者・復元条件である。技術案と比較費用はY0に記録した。現turnは停止前の設計保存だけを行い、実データ転送、service公開、worker起動はしない。

## Options Considered

以下の費用・運用評価は全て推定で、計測した工数ではない。トポロジーの(c)は決定済みである。

| 案 | 費用と運用 | 判定 |
|---|---|---|
| 1つの辞書ファイルを同期 | 推定: 部品は少ないが、全体上書きの競合処理が要る | 削除と学習の履歴を保てないため採らない |
| 中央peer＋local記録を先行し、後にpeer間交換 | 推定: 最初の受信口と運用先を絞れる。後でpeer一覧と各機械の公開口が増える | 所有者が選んだ(c)。同じ記録とprotocolを使う |
| 最初から全機械で分散 | 推定: 認証・発見・端末の常駐性を初期段階から扱う | 後の段へ回す |
| サーバーだけに学習を保存 | 推定: local保存は減るが、切断時の入力と復旧が弱い | local cacheを求める回答を満たさない |
| syncとlookupを一体化 | 推定: 初期の配線は減るが、公開範囲とdata権限が結合する | moduleを分ける決定に従い採らない |

## Trade-off Analysis

中央先行は、記録の保存とまとめを保ち、最初に守る受信口を絞る。将来も、認証した相手が中央か端末かでrecord identityを変えない。手元のログは切断中の学習を失わないためにも必要であり、検索結果だけのcacheでは足りない。

サーバーを使っても、複数機械での学習の衝突を到着順で解決しない。全機械が同じ記録集合を持つまで即時の一致は求めず、同じ集合になった時点の一致を検証する。

記録は増え続ける。削除記録の保持、長期切断した機械、復元時の機械 ID の扱いを決めるまでは、古い記録を畳まない。

## Consequences

- `jisyo` の記録、まとめ、IME 形式への変換はサーバーに依存させない。
- jisyo `776f663` のServer-exchange boundaryに合わせ、ローカルのsyncとnetwork交換を分ける。前者をnetworkやack待ちに結び付けない。
- PLANのY0〜Y3を使い、boiled/localhostでの合成試験を先に行う。本番hostの最終選択前でも設計は特定環境に固定しない。
- machine IDの喪失・再利用、圧縮、署名/E2E、将来lookupのdata権限は別の設計を要する。今回それらを実装・検証済みにはしない。
