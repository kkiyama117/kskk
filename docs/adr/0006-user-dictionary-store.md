# ADR-0006: ユーザー辞書は機械ごとの追記だけの記録で持ち、全機械の記録を順序に依らずまとめる

- Status: Proposed
- Date: 2026-11-06
- Deciders: kiyama
- Level: L2
- Phase: 2、4〜9
- Supersedes: なし

## Context

ユーザーは機械ごとに別の学習の辞書を持っている。fcitx5-skk は `user.dict` (EUC-JP)、skkeleton は `~/.skkeleton` (UTF-8)、CorvusSKK は `userdict.txt` (BOM 付き UTF-16LE) である (`docs/research/README.md`)。

どの実装も、メモリ上の辞書でファイル全体を書き直す (`docs/research/sync.md`)。そのため、共有フォルダで1つのファイルを複数の機械が使うと、互いの学習を上書きして単語を失う。和集合でまとめる方法では、消した単語が別の機械から戻ってくる。skkserv の命令は検索だけで、書き込みができない。辞書を機械の間で同期する既存の仕組みはない。

この ADR は、保存と同期の方針と、その判定の基準を決める。記録の1行の項目、ファイルの形式、文字コードの扱いは `skk-jisyo` が `jisyo/SPEC.md` に書く。

## Decision

1. **機械ごとの記録**: 各機械は、自分の記録のファイルにだけ追記する。ほかの機械の記録は読むだけで、書き換えない。2台が同じファイルを書くことはない。
2. **記録の中身**: 学習の操作 (候補の追加、先頭への移動、削除、注釈だけの変更) を1件ずつ記録する。1件は、エンジンが出す学習のイベント (ADR-0009 の `jisyo::LearnEvent`) に、機械の ID、連番、時刻を付けたものである。削除も記録として残す。辞書の今の姿は記録から計算する。
3. **順序に依らないまとめ**: 全機械の記録を読んで1つの辞書を作る。どの順で読んでも、同じ記録を2度読んでも、結果は同じになる。各記録の前後関係は、記録自身が持つ情報 (時刻と機械の ID など。詳細は `jisyo/SPEC.md`) だけで決まる。
4. **同期は外の道具に任せる**: 記録のファイルを置いたフォルダを、機械の間でファイルを同期する何かで同期する。私たちは、ファイルの同期以外 (ロック、サーバー、常時の接続) を前提にしない。
5. **今の IME への橋渡し**: 私たちのエンジンに移るまでは、まとめた辞書を CorvusSKK、fcitx5-skk、skkeleton の形式で書き出す。IME が書き直したファイルは、前回の書き出しと比べて、違いを記録に直して取り込む。
6. **エンジンとの関係**: 私たちのエンジン (ADR-0004) は、学習のたびに記録を1件追記する。ファイル全体を書き直さない。

## 決め方

方針は実験で決まる。`jisyo` の検査が次の基準を満たせば、この方針で足りるとする。ユーザーには聞かない。

判定の基準 (どれも合成のデータで、`jisyo` の `make check` で確かめる):

- 2台分の記録を、どちらの順でまとめても、同じ辞書のバイト列になる。3台分では、6通りの順のすべてで同じになる。
- 同じ記録を2度まとめても、1度のときと同じ辞書になる。
- A で消した単語は、B の古い記録 (消す前の時刻の追加) をまとめても戻らない。消した後に追加されたときだけ戻る。
- 記録のファイルの末尾が書きかけで切れていても、それより前の記録はすべて読める。切れた1件だけが捨てられ、その件数が報告される。
- IME が読み直さずに古い中身で上書きしても、前回の書き出しで IME に渡したばかりの単語に `Delete` は記録されない。届いた単語が1語でも、この基準は成り立つ (削除の数の上限だけに頼らない)。
- 前回の書き出しと違う IME のファイルを取り込むと、期待どおりの追加、先頭への移動、削除の記録になる。違いがなければ記録は1件も増えない。
- 各形式への書き出しが、合成のデータで、その形式の読み手 (`jisyo` の読み込み) で読み戻せる。

同期の道具 (Syncthing、Git、クラウドのドライブなど) は人が決める。ただし設計は「ファイルが同期されるフォルダ」しか前提にしないので、決まるまではこの機の1つのフォルダで作り、試す。急ぎの問いではない (PLAN.md の問い4)。

## Options Considered

| 案 | 複雑さ | 費用 | 運用の手間 | 要点 |
|---|---|---|---|---|
| A. 1つの辞書ファイルを同期する | 低 | 低 | 高 | 今の IME のまま使える。2台が書き直すと単語を失う。削除が戻る。CorvusSKK の UTF-16LE と変換が要る |
| B. 機械ごとの追記だけの記録を、順序に依らずまとめる (推奨) | 中 | 中 | 低 | 書き手が機械ごとに1人なので失わない。削除も記録に残る。今の IME には書き出しと取り込みで橋渡しする |
| C. 自分のサーバーに書き込みの命令を足す | 高 | 高 | 高 | 1か所に集まる。常にサーバーにつながる必要があり、Android やオフラインで困る。全部のクライアントに手を入れる |

## Trade-off Analysis

B は、同時に同じファイルを書く場面をなくすことで、失う原因そのものを取り除く。C も同じことができるが、常時の接続とサーバーの保守が要る。A は今すぐ使えるが、単語を失うという問題を残す。

B で捨てるもの: 記録はずっと増え続ける。学習1回あたり1行なので、年に数万行の程度と見込む (推測)。大きくなったら、全機械が読んだ時点までをまとめた写し (snapshot) を作って古い記録を畳む方法を、後で決める。

## Consequences

- 楽になること: エンジンの学習と、IME から取り込んだ学習が、同じ型の記録になる (ADR-0009)。どの機械でも、同期が済めば同じ辞書になる。削除が戻らない。辞書を失っても、記録から作り直せる。
- 難しくなること: 今の IME は記録を書けないので、書き出しと取り込みの道具 (`jisyo`) が要る。IME が書き直したファイルからは「いつ」が分からないので、取り込んだ時刻で記録する。
- 見直す条件: 記録が大きくなって読むのが遅くなったとき (たとえばまとめに 100 ms を超えたとき)。時計が大きくずれた機械があって、先頭への移動の順が目に見えて狂うとき。
