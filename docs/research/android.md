# SKK on Android: existing IMEs, IME construction, native cores, sync, and distribution

The owner wants one SKK that behaves and stores the same on Windows (CorvusSKK), Linux (ibus-skk), Vim (skkeleton, at risk because denops may stop being maintained), and later Android. This slice answers what already exists on Android, what it takes to build one, and how its data can be shared. The smallest useful output is the cited comparison below plus the blockers it exposes. Today is 2026-11-06.

## 1. Existing SKK IMEs for Android

All four live projects descend from minghai's 2009 Android port and 海月玲二 (ray-mizuki)'s flick and hard-key rework; `ikeji/AndroidSKK` is a 2012 archive that names those ancestors and the original branches [fetched: https://github.com/ikeji/AndroidSKK].

**SKK for Android, `deadend-noname/AndroidSKK`.** Repository https://github.com/deadend-noname/AndroidSKK [fetched]. License Apache-2.0, from the `LICENSE` file at the repository root [fetched: https://raw.githubusercontent.com/deadend-noname/AndroidSKK/main/LICENSE]. Latest release v3.7.2 on 2026-03-15 [fetched: https://github.com/deadend-noname/AndroidSKK/releases.atom]. Latest commit `4a6a288` on 2026-03-15 [fetched: https://github.com/deadend-noname/AndroidSKK/commits/main.atom]. Features read from its README: a flick soft keyboard with light and dark themes, an abbrev keyboard, a QWERTY English keyboard, a hardware-keyboard path with sticky shift and space-as-shift, several dictionaries at once, a personal dictionary with a learning and maintenance tool, and a built-in dictionary derived from SKK-JISYO.L that it unpacks on first launch [snippet: repository README rendered on the repository page].

**Android SKK for Physical Keyboard, `kachaya-ime/AndroidSKK`.** Repository https://github.com/kachaya-ime/AndroidSKK [fetched]. License Apache-2.0 [fetched: https://raw.githubusercontent.com/kachaya-ime/AndroidSKK/master/LICENSE]. Latest release 3.3.0 on 2026-10-17 and latest commit `6200d04` on 2026-10-17 [fetched: https://github.com/kachaya-ime/AndroidSKK/releases.atom and https://github.com/kachaya-ime/AndroidSKK/commits/master.atom]. It targets phones with real keyboards (Unihertz Titan, Clicks Keyboard), offers a QWERTY soft keyboard or a one-row symbol bar, and lets the user drag-edit key layouts [snippet: repository README]. Release 2.2.0 on 2026-09-12 added an importer for external SKK dictionaries [fetched: releases.atom above]. Release 3.3.0 moved its reconversion feature to zenz with llama.cpp [fetched: same feed].

**`tamo/AndroidSKK`.** Repository https://github.com/tamo/AndroidSKK [fetched]. License Apache-2.0 per the repository page [snippet: https://github.com/tamo/AndroidSKK]. Latest release 3.7 on 2024-08-03 [fetched: https://github.com/tamo/AndroidSKK/releases.atom]. Latest commit `91ab8fe` on 2026-07-12 [fetched: https://github.com/tamo/AndroidSKK/commits/master.atom]. It has a GUI flick-rule editor, a dictionary download list that accepts EUC-JP gzip files, searchable and editable personal dictionary entries, and H2 MVStore as its store [snippet: repository README]. MVStore is a binary database, so this fork's learned words are not a plain SKK file [snippet: same README].

**SKKepsis, `TPKato/skkepsis`.** Repository https://github.com/TPKato/skkepsis [fetched]. License GPL-3.0 [fetched: https://raw.githubusercontent.com/TPKato/skkepsis/main/LICENSE]. Latest release v0.2 on 2026-03-22 [fetched: https://github.com/TPKato/skkepsis/releases.atom]. Latest commit `12e38dd` on 2026-03-22 [fetched: https://github.com/TPKato/skkepsis/commits/main.atom]. Its soft keyboard is QWERTY only, with three layouts (US-like, US compact in five rows, US compact in six rows), and hardware keys are explicitly not supported or tested [snippet: https://www.chinpui.org/hack/softwares/skkepsis/]. It accepts only UTF-8 text dictionaries, takes the personal dictionary from a user-chosen directory, fixes the personal file name to `skk-userdict.txt`, and stores okuri-ari and okuri-nasi entries without sorting or distinguishing them [snippet: same page].

**`xiupos/android-skk`.** Archived by its owner on 2024-08-25, last push 2023-04-01, single prerelease v0.1.0 on 2021-12-30 [snippet: https://github.com/xiupos/android-skk and https://github.com/xiupos/android-skk/releases]. A multilingual rework of the same lineage, dead in practice.

**Projects that are not SKK.** AnySoftKeyboard has no Japanese pack and no SKK fork I could find; its Japanese requests are open issues #1233 (2018, last comment 2023) and #1969 (2020, last comment 2022) [snippet: https://github.com/AnySoftKeyboard/AnySoftKeyboard/issues/1233 and /issues/1969]. Hacker's Keyboard is Apache-2.0 and its own README calls it ancient and unlikely to keep working on modern Android [snippet: https://github.com/klausw/hackerskeyboard]. SKKIME is a Windows IME, and its 1.5改 line ended with the author pointing users at SKKFEP [snippet: http://coexe.web.fc2.com/skkime.html]. CorvusSKK, the owner's Windows input method, is at 3.3.4 dated 2026-08-14 [snippet: https://nathancorvussolis.github.io/].

**Distribution of the SKK IMEs.** None of them has a store listing I found. Each tells users to download an APK from GitHub Releases; SKKepsis additionally names a file manager or `adb` [snippet: https://www.chinpui.org/hack/softwares/skkepsis/]. No SKK IME appeared in the F-Droid results I saw; the only Japanese engine there is Fcitx5's Anthy plugin [snippet: https://f-droid.org/en/packages/org.fcitx.fcitx5.android.plugin.anthy/].

## 2. How an Android IME is built

The system-side contract has three required pieces. The app declares a service with permission `android.permission.BIND_INPUT_METHOD`, an intent filter for `android.view.InputMethod`, and meta-data named `android.view.im` that points at an XML resource [snippet: https://developer.android.com/develop/ui/views/touch-and-input/creating-input-method]. Fcitx5 for Android's manifest is a live example of exactly that shape, with `directBootAware="true"` and `android:exported="true"` [fetched: https://raw.githubusercontent.com/fcitx5-android/fcitx5-android/master/app/src/main/AndroidManifest.xml].

The engine talks to the editor through `InputConnection`, reached with `getCurrentInputConnection()` [snippet: creating-input-method page]. The composing region is the mechanism SKK maps onto: `setComposingText` replaces the current composing span, `finishComposingText` ends it, and `setComposingRegion` restores a span the editor dropped [snippet: https://developer.android.com/reference/android/view/inputmethod/InputConnection]. The reference also says the composing span and the selection are independent, which is why an IME cannot assume the cursor sits inside its preedit [snippet: same page].

Fcitx5 for Android shows the working pattern in one file. It keeps its own composing range and formatted preedit, calls `setComposingText` with the highlighted span, calls `setComposingRegion` when the editor's composing span vanishes, guards the whole write in `beginBatchEdit`/`endBatchEdit`, and drives commit through `commitText` or `sendKeyEvent` [fetched: https://raw.githubusercontent.com/fcitx5-android/fcitx5-android/master/app/src/main/java/org/fcitx/fcitx5/android/input/FcitxInputMethodService.kt].

The candidate view has two shapes. The framework offers `onCreateCandidatesView` plus `setCandidatesViewShown`, and the default returns null [snippet: creating-input-method page and https://developer.android.com/reference/android/inputmethodservice/InputMethodService]. Fcitx5 skips that and puts its own `CandidatesView` in the content view, replacing it on theme change, so it can float the same panel when a physical keyboard is attached [fetched: FcitxInputMethodService.kt above].

Hardware key events arrive two ways. `onKeyDown` and `onKeyUp` fire while the IME holds input focus; Fcitx5 overrides both, converts each `KeyEvent` to a fcitx key symbol and state, and posts it to the engine, then re-emits the engine's answer with `sendKeyEvent` while repairing meta state with `clearMetaKeyStates` [fetched: FcitxInputMethodService.kt above]. Its `InputDeviceManager` switches between the full virtual keyboard and the floating candidate panel by device [fetched: same file].

Cursor anchoring uses `CursorAnchorInfo`. Fcitx5 overrides `onUpdateCursorAnchorInfo`, maps the character bounds through the reported matrix, and falls back to the bottom-left corner when the anchor is unavailable, including the API 35 case its release notes name [fetched: FcitxInputMethodService.kt and https://github.com/fcitx5-android/fcitx5-android/releases.atom].

Jetpack Compose works in an IME but needs three owners attached by hand. An `InputMethodService` is not an Activity, so Compose's `ComposeView` fails with "Composed into the View which doesn't propagate ViewTreeLifecycleOwner" until the service implements `LifecycleOwner`, `ViewModelStoreOwner` and `SavedStateRegistryOwner` and sets them on the decor view before returning the compose view from `onCreateInputView` [snippet: https://stackoverflow.com/questions/65755763/ and the working example at https://github.com/THEAccess/compose-keyboard-ime/blob/main/app/src/main/java/com/example/composeime/IMEService.kt].

The minimal set for an SKK IME is therefore small. A service plus manifest and `method.xml`. An `InputMethodService` subclass that returns a view from `onCreateInputView`. A pure engine object holding the SKK state machine and dictionaries. An adapter that turns engine state into `setComposingText`, `finishComposingText` and `commitText` calls. A candidate strip. A hardware-key funnel into the same engine. A settings activity for dictionaries and key behaviour. Persistent storage for the personal dictionary. Everything else, including theming, emoji, clipboard and inline suggestions, is optional.

## 3. Embedding a shared native core

**The `jni` crate.** Version 0.22.4, published 2026-09-19, MIT or Apache-2.0 [fetched: https://docs.rs/jni/latest/jni/]. A native method is an `extern "system"` function, exposed either by a JVM-mangled name such as `Java_HelloWorld_hello` or registered at runtime with `Env::register_native_methods`, and the crate must build with `crate-type = ["cdylib"]` [fetched: same page].

**cargo-ndk.** One command cross-compiles and lays out the libraries where Gradle looks, `cargo ndk -t armeabi-v7a -t arm64-v8a -o ./jniLibs build --release`, after `rustup target add aarch64-linux-android ...`; it also provides `cargo ndk-test` to run tests over `adb` and `cargo ndk-env` to export the environment [fetched: https://raw.githubusercontent.com/bbqsrc/cargo-ndk/main/README.md]. License is Apache-2.0 or MIT [fetched: same README].

**UniFFI.** A bindings generator that compiles Rust into a shared library and generates Kotlin, Swift, Python and Ruby bindings from an interface definition or proc-macros; Mozilla uses it in Firefox for both Kotlin (Android) and Swift (iOS), and it is MPL-2.0 [snippet: https://github.com/mozilla/uniffi-rs/]. Kotlin generation is `cargo run --bin uniffi-bindgen generate --library target/release/libmath.so --language kotlin --out-dir out` [snippet: https://mozilla.github.io/uniffi-rs/latest/tutorial/foreign_language_bindings.html].

The choice matters for scope. Plain `jni` keeps the boundary hand-written and minimal, which suits an engine with a handful of calls such as feed key, take preedit, take candidates, commit. UniFFI buys generated Kotlin types and error handling, and costs an interface definition plus a codegen step that must be wired into Gradle. For an SKK core whose API is a dozen calls, `jni` is the smaller commitment [inference from the two sources above].

**Precedents.** Mozc builds an Android library, `libmozc.so`, and is BSD-3-Clause [snippet: https://github.com/google/mozc/]. Google removed the Android client app from that repository deliberately, stating that the team could not keep maintaining it, and pointed at forks including `elizagamedev/android-libre-japanese-input`, `kachaya/MozcForAndroid` and `Lee0701/mozc-android` [snippet: https://github.com/google/mozc/discussions/879]. Trime is a Kotlin front end over librime through JNI, built from submodules with the NDK and CMake, under GPL-3.0 [snippet: https://github.com/osfans/trime and https://github.com/osfans/trime/blob/develop/LICENSE]; its latest commit is `0f7bc78` on 2026-11-01 on `develop`, and the same day bumped the version to 3.3.14 [fetched: https://github.com/osfans/trime/commits/develop.atom], while the newest tag shown on its releases page was v3.3.12 dated 01 Sep, with the year not visible in the excerpt I saw [snippet: https://github.com/osfans/trime/releases].

Fcitx5 for Android is the most instructive case. It vendors fcitx5 as git submodules and builds it with the NDK and CMake 3.22.1 [snippet: https://github.com/fcitx5-android/fcitx5-android]. At runtime fcitx5 runs as a separate process behind a bound service, `FcitxRemoteService`, protected by a signature-level permission the app defines, and Kotlin reaches it through `FcitxDaemon.connect` and `FcitxConnection` [fetched: the manifest and `FcitxInputMethodService.kt` above]. The Kotlin side calls a `FcitxAPI` interface whose suspend functions are dispatched onto the fcitx thread, with a `SharedFlow` of events for commits, preedit, key events and input-method switches [snippet: https://raw.githubusercontent.com/fcitx5-android/fcitx5-android/master/app/src/main/java/org/fcitx/fcitx5/android/core/FcitxAPI.kt]. Engines ship as separate APKs, one plugin per engine, and the host discovers them through a plugin action and a signature permission, which is why its release page lists `plugin.anthy`, `plugin.rime`, `plugin.hangul` and others as separate downloads [fetched: manifest above and https://github.com/fcitx5-android/fcitx5-android/releases.atom]. Latest release is 0.1.3 on 2026-07-26 and latest commit `eb5b502` on 2026-10-13 [fetched: releases.atom and https://github.com/fcitx5-android/fcitx5-android/commits/master.atom]. License is LGPL-2.1 [snippet: https://github.com/fcitx5-android/fcitx5-android and https://f-droid.org/en/packages/org.fcitx.fcitx5.android/].

SKK has no place in that structure yet. Japanese in fcitx5-android comes only from the Anthy plugin [snippet: repository README]. The project has an open issue titled "Japanese input support using SKK", and its Mozc plugin is an open pull request #667 last updated 2026-04-20 [snippet: https://github.com/fcitx5-android/fcitx5-android/issues/782 and https://github.com/fcitx5-android/fcitx5-android/pull/667]. Desktop fcitx5 does have `fcitx5-skk`, an engine over libskk [fetched by search snippet: https://github.com/fcitx/fcitx5-skk/], but nothing indicates it was ported. Adding SKK there would mean building libskk against the NDK inside the plugin APK, or writing an addon that wraps a Rust engine, and both routes inherit the daemon, IPC and plugin machinery.

## 4. Data sync on Android

The Storage Access Framework is the portable answer. A client app fires `ACTION_OPEN_DOCUMENT` for one file, available since API 19, or `ACTION_OPEN_DOCUMENT_TREE` for a directory, available since API 21, and the system picker returns content URIs from any provider including cloud drives [snippet: https://developer.android.com/guide/topics/providers/document-provider]. Long-term access needs `takePersistableUriPermission` with the persistable flag, and `getPersistedUriPermissions` lists what you hold [snippet: https://stackoverflow.com/questions/32563428 and https://commonsware.com/blog/2016/05/03/storage-access-framework-faq.html]. `DocumentFile` then works inside a tree URI [snippet: the commonsware FAQ].

Existing IMEs already rely on this. SKKepsis asks the user for a personal-dictionary directory and a system dictionary file, both UTF-8 text, with the personal file fixed at `skk-userdict.txt` in the chosen directory [snippet: https://www.chinpui.org/hack/softwares/skkepsis/]. That is SAF-backed import and export with the file itself as the interchange unit. Kachaya added an external SKK dictionary importer in 2.2.0 [fetched: releases.atom above]; the release notes describe import only, so export is unconfirmed. Tamo's MVStore store is the outlier, since a binary store does not travel [snippet: repository README].

Exposing your own storage as a document provider is the second half of the pattern, and fcitx5-android does it. Its manifest registers `FcitxDataProvider` with authority `${applicationId}.provider`, the `MANAGE_DOCUMENTS` permission and the `android.content.action.DOCUMENTS_PROVIDER` intent filter, so the app's data directory appears in the system file picker [fetched: manifest above]. Release 0.1.1 added an option to open DocumentsUI and browse the user data directory [fetched: https://github.com/fcitx5-android/fcitx5-android/releases.atom]. A sync app can then read and write that tree without root.

Encoding is the practical hazard for the owner. The Windows and terminal side uses SKK-JISYO-style plain text; SKKIME's personal dictionary was UTF-16LE with a BOM while DDSKK's `.skk-jisyo` was EUC-JP in the same 2013 note [snippet: https://uep.media.hosei.ac.jp/skkime-ddskk-ユーザ辞書の共有/]. CorvusSKK keeps `userdict.txt` under `%APPDATA%\CorvusSKK` [snippet: https://github.com/nathancorvussolis/corvusskk], and I did not verify its encoding.

Whole-file rewrite is the second hazard. A synced folder plus a text dictionary means two devices can each rewrite the file and lose the other's words, and SKKepsis already warns that its saves do not preserve okuri-ari versus okuri-nasi ordering, so even a successful copy is not a clean merge [snippet: SKKepsis page]. Any design that syncs by file needs either a single writer or an append-and-merge step, and that choice is mine to flag rather than one the sources settle [inference].

## 5. Distribution

**F-Droid.** The main repository takes only FLOSS apps, builds them from published source, forbids proprietary tracking and analytics libraries, and reviews dependencies for non-free parts [snippet: https://f-droid.org/docs/Inclusion_Policy/]. Apps should be actively maintained, have run for at least three months, and carry fastlane-style metadata before inclusion [snippet: https://f-droid.org/docs/Submitting_to_F-Droid_Quick_Start_Guide/ and the inclusion policy]. Reproducible builds are encouraged and not required, and F-Droid signs with its own key, which means a user cannot upgrade in place between a developer-signed and an F-Droid-signed build [snippet: https://f-droid.org/docs/Reproducible_Builds/ and https://f-droid.org/docs/Building_Applications/]. A Rust core is acceptable in principle, since prebuilt FLOSS binaries from Rust and Rustup are named as tolerable sources [snippet: inclusion policy].

**Google Play.** I found no policy page aimed at IMEs specifically [checked: the Play policy results I saw contain no IME-specific document]. The rules that bind an IME are the general ones. Its user data policy covers personal and sensitive data, requires disclosure of collection and sharing, a privacy policy in both the listing and the app, and a Data safety declaration, and requires affirmative consent before sensitive access [snippet: https://support.google.com/googleplay/android-developer/answer/10144311]. The permissions policy restricts requesting data not needed for promoted features [snippet: https://support.google.com/googleplay/android-developer/answer/16558241]. New apps and updates must target Android 16, API level 36, from 2026-08-31, with an extension available to 2026-11-01 [snippet: https://support.google.com/googleplay/android-developer/answer/11926878]. Signing differs per channel; fcitx5-android warns that its GitHub, F-Droid and Jenkins APKs share one certificate while its Play APKs use another, so upgrades across the two are incompatible [snippet: repository README].

**Sideloading.** Every SKK IME here ships release APKs and asks the user to install them, which requires allowing installs from the browser or file manager, or using `adb install` [snippet: SKKepsis page]. Updates stay manual unless the app self-updates, which the F-Droid policy treats as a binary download needing opt-in consent [snippet: inclusion policy].

For this project the low-friction path is GitHub Releases first, with an F-Droid listing once the app has three months of history and clean dependencies, and Play only if the data policy work and the second signing key are acceptable [inference].

## Open questions

CorvusSKK's user dictionary encoding is unverified, and it decides whether a shared text file survives the round trip to Windows, since the 2013 SKKIME and DDSKK example shows UTF-16 and EUC-JP in the same workflow [snippet: https://uep.media.hosei.ac.jp/skkime-ddskk-ユーザ辞書の共有/].

Whether `deadend-noname` or `kachaya-ime` can export the personal dictionary as plain text for another machine is not documented in anything I read. Kachaya's importer is the only confirmed cross-machine path, and it is one direction.

Whether libskk, the backend of desktop `fcitx5-skk`, builds under the Android NDK is untested here. That decides whether SKK inside fcitx5-android is a port or a rewrite.

The body of fcitx5-android issue #782 could not be read, because the fetcher returned page navigation only, so only its title and the pull-request cross-reference are known.

Android platform pages were also truncated to navigation, so every platform claim above is labelled [snippet] rather than read in full.

No source I read measured anything about these IMEs. Latency, dictionary load time and candidate quality for SKK on a phone are unknown.

The Play claim rests on general policies, not an IME-specific document, because none was found.
