# SKK in Vim, Neovim, and Emacs, and the denops risk

The owner wants one SKK engine with the same behavior and the same dictionary data on Windows, Linux, and Vim/Neovim, and possibly on Android later. This slice reports what the editor side offers today and what the evidence says about the denops risk. skkeleton is the most complete Vim/Neovim SKK and is actively maintained, but it turns every keystroke into a blocking call into a Deno process. denops.vim is alive, while the Deno runtime it depends on lost its company on 2026-10-09 and is promised fixes only until roughly October 2027. Read-only investigation, so no throughput checkpoint applies. All dates below are from the pages I fetched on 2026-11-06.

## 1. skkeleton

Repository and license. The repository is `vim-skk/skkeleton` and the license is zlib, with "Copyright (c) 2021 kuuote" in the license text [fetched] https://raw.githubusercontent.com/vim-skk/skkeleton/main/LICENSE . The README states "zlib license" and "Required Deno 1.42.0+ now" [fetched] https://raw.githubusercontent.com/vim-skk/skkeleton/main/README.md .

Latest release and commits. The latest release is 3.0.0, published 2026-09-11 [fetched] https://github.com/vim-skk/skkeleton/releases.atom . The latest commit I saw is 2026-10-31T06:08:24Z, a dependabot merge by Shougo [fetched] https://github.com/vim-skk/skkeleton/commits/main.atom . The last hand-written functional change in that feed is 2026-10-16, "fix: take back a kakutei confirmed by typing on a vowel" by delphinus, merged by Shougo [fetched] https://github.com/vim-skk/skkeleton/commits/main.atom . Maintainer activity in 2026 therefore shows a release in September and code review plus a contributor fix in October, mixed with dependabot merges [fetched] https://github.com/vim-skk/skkeleton/commits/main.atom .

Architecture. The Deno side is TypeScript, entered from `denops/skkeleton/main.ts`, which imports the config, keymap, dictionary, kana table, state, and completion modules and registers a dispatcher [fetched] https://raw.githubusercontent.com/vim-skk/skkeleton/main/denops/skkeleton/main.ts . The Vim script side owns mappings, popup drawing, and notation. Each mapped key runs `<Cmd>call skkeleton#handle(...)`, and `skkeleton#handle` calls `skkeleton#request('handle', ...)`, which wraps `denops#request('skkeleton', ...)` [fetched] https://raw.githubusercontent.com/vim-skk/skkeleton/main/autoload/skkeleton.vim . So the input state machine and the dictionaries live in Deno, and Vim only forwards keys and applies the returned key sequence [fetched] https://raw.githubusercontent.com/vim-skk/skkeleton/main/autoload/skkeleton.vim .

Tested versions. The bundled help says tests run on Vim v9.1.1646 and Neovim 0.11.3 or later [fetched] https://raw.githubusercontent.com/vim-skk/skkeleton/main/doc/skkeleton.jax .

Main config options. `skkeleton#config()` takes a dictionary; the documented keys are `acceptIllegalResult`, `completionBackend` (default "native"), `completionRankFile`, `databasePath`, `debug`, `eggLikeNewline`, `globalDictionaries`, `globalKanaTableFiles`, `immediatelyCancel`, `immediatelyDictionaryRW`, `immediatelyOkuriConvert`, `kanaTable`, `keepMode`, `keepState`, `lowercaseMap`, `markerHenkan`, `markerHenkanSelect`, `registerConvertResult`, `selectCandidateKeys`, `setUndoPoint`, `showCandidatesCount`, `skkServerHost`, `skkServerPort`, `skkServerReqEnc`, `skkServerResEnc`, `skkServerTimeout`, `sources`, and `userDictionary` [fetched] https://raw.githubusercontent.com/vim-skk/skkeleton/main/doc/skkeleton.jax . Since 2026-09-10 the completion backend must be named explicitly, and automatic detection is gone [fetched] https://raw.githubusercontent.com/vim-skk/skkeleton/main/doc/skkeleton.jax .

User dictionary path and format. `userDictionary` defaults to `~/.skkeleton` and is one file, UTF-8 only because of a JavaScript constraint [fetched] https://raw.githubusercontent.com/vim-skk/skkeleton/main/doc/skkeleton.jax . The file is plain SKK text with the blocks `;; okuri-ari entries.` and `;; okuri-nasi entries.`, one entry per line as `よみ /候補/候補/`, and the writer sorts okuri-ari entries in reverse and okuri-nasi entries forward [fetched] https://raw.githubusercontent.com/vim-skk/skkeleton/main/denops/skkeleton/sources/user_dictionary.ts . Candidate rank data goes to a separate JSON file when `completionRankFile` is set [fetched] https://raw.githubusercontent.com/vim-skk/skkeleton/main/denops/skkeleton/sources/user_dictionary.ts .

Dictionary sources. `sources` defaults to `["skk_dictionary"]`, and the user dictionary is always used regardless of that list [fetched] https://raw.githubusercontent.com/vim-skk/skkeleton/main/doc/skkeleton.jax . The four documented sources are `skk_dictionary` for files listed in `globalDictionaries`, `deno_kv` for a Deno KV cache that needs `databasePath` and `--unstable-kv`, `skk_server` for an SKK dictionary server over TCP, and `google_japanese_input` for the Google Japanese Input web API, which needs network access and does not support completion [fetched] https://raw.githubusercontent.com/vim-skk/skkeleton/main/doc/skkeleton.jax . Global dictionary files may be given with an encoding or left to auto-detection, and compressed dictionaries are not read directly [fetched] https://raw.githubusercontent.com/vim-skk/skkeleton/main/doc/skkeleton.jax . Besides plain SKK text, the file source also loads `.yaml`, `.yml`, `.json`, and msgpack dictionaries [fetched] https://raw.githubusercontent.com/vim-skk/skkeleton/main/denops/skkeleton/sources/skk_dictionary.ts . The skkserv client defaults are host `127.0.0.1`, port 1178, request and response encoding `euc-jp`, and a 5000 ms timeout per exchange [fetched] https://raw.githubusercontent.com/vim-skk/skkeleton/main/doc/skkeleton.jax . skkeleton needs denops.vim v8 or later, and a `denopsv7` branch exists for older denops [fetched] https://raw.githubusercontent.com/vim-skk/skkeleton/main/doc/skkeleton.jax .

## 2. denops.vim

Maintainers. The documentation says "Denops is primarily developed and maintained by the vim-denops organization (separated from the vim-jp organization)" [fetched] https://vim-denops.github.io/denops-documentation/ . The README says "Denops is mainly developed by members of vim-jp" [fetched] https://raw.githubusercontent.com/vim-denops/denops.vim/main/README.md . In the commit feeds I saw merges by Shougo and lambdalisue, plus a test fix by haruyama [fetched] https://github.com/vim-denops/denops.vim/commits/main.atom .

Latest release and commits. The latest release is v8.0.2, published 2026-03-22 by lambdalisue [fetched] https://github.com/vim-denops/denops.vim/releases.atom . The latest commit I saw is 2026-10-31T06:13:38Z, a dependabot merge by Shougo [fetched] https://github.com/vim-denops/denops.vim/commits/main.atom . The feed also shows "Remove release workflows" on 2026-10-13 and test fixes on 2026-10-12 [fetched] https://github.com/vim-denops/denops.vim/commits/main.atom . I did not read the reasoning behind removing the release workflows.

Supported versions. The README badges state Deno 2.3.0 or above, Vim 9.1.1646 or above, and Neovim 0.11.3 or above [fetched] https://raw.githubusercontent.com/vim-denops/denops.vim/main/README.md . The same README says the policy supports the two most recent minor versions of Neovim and Deno when a major version is cut [fetched] https://raw.githubusercontent.com/vim-denops/denops.vim/main/README.md .

Public statement about the future. I found none. The README, the documentation introduction, and the release feed contain no statement about the Deno announcement or about denops' own future, as of 2026-11-06 [fetched] https://raw.githubusercontent.com/vim-denops/denops.vim/main/README.md , [fetched] https://vim-denops.github.io/denops-documentation/ , [fetched] https://github.com/vim-denops/denops.vim/releases.atom .

Deno itself. On 2026-10-09 Ryan Dahl announced that "the entire Deno team is joining Cloudflare" and that "we will support the Deno runtime for another year with monthly releases containing bug fixes and security updates. After that year we will end our development of the Deno runtime" [fetched] https://deno.com/blog/cloudflare . The pinned repository issue restates this as maintenance "until October 2027", monthly 2.9.x LTS releases, no new feature work, and reverts of canary-only features, and adds that Deno is MIT licensed and may be forked [fetched] https://github.com/denoland/deno/issues/37030 . The runtime is still shipping fixes. The latest release I saw is v2.9.8 on 2026-10-21 and the latest commit 2026-10-26 [fetched] https://github.com/denoland/deno/releases.atom , [fetched] https://github.com/denoland/deno/commits/main.atom . An earlier docs change had promised the v2.9 line as LTS only until 2026-12-31, so the published support horizon moved after the acquisition [snippet] https://github.com/denoland/docs/pull/3397 .

What the evidence shows about the owner's fear. denops.vim has commits in the last three weeks of October 2026 and no deprecation notice [fetched] https://github.com/vim-denops/denops.vim/commits/main.atom . Its only runtime is Deno, whose corporate steward announced an end to runtime development after about one year, with security and bug fixes until October 2027 and an explicit invitation to fork [fetched] https://deno.com/blog/cloudflare , [fetched] https://github.com/denoland/deno/issues/37030 . The two facts together are the whole basis of the risk. Nothing I read says denops will stop, and nothing I read says Deno will keep being developed past 2027. A Vim setup built on skkeleton therefore depends on a chain of two projects where the lower one has a published end date for development and a published fix window.

## 3. Alternatives without denops

eskk.vim. Repository `vim-skk/eskk.vim`, pure Vim script, described as "pure Vim script implementation of input method engine SKK" [snippet] https://github.com/vim-skk/eskk.vim . The license is the New BSD license in the help file, and the repository root has no LICENSE file [fetched] https://raw.githubusercontent.com/vim-skk/eskk.vim/master/doc/eskk.jax , [fetched] https://codeload.github.com/vim-skk/eskk.vim/tar.gz/refs/heads/master . The latest commit I saw is 2026-05-11, "Fix g:eskk#keep_state", with several 2026 contributions by kyouryuukunn [fetched] https://github.com/vim-skk/eskk.vim/commits/master.atom . There are no GitHub releases, and the open issue count is 63 [fetched] https://github.com/vim-skk/eskk.vim/releases.atom , [snippet] https://github.com/vim-skk/eskk.vim . Functionally it covers okuri-ari and okuri-nasi conversion, kana tables including AZIK, candidate selection, dictionary save and backup, and skkserv through `g:eskk#server`, which needs a channel or Neovim [fetched] https://raw.githubusercontent.com/vim-skk/eskk.vim/master/doc/eskk.jax . It also ships a ddc source at `denops/@ddc-sources/eskk.ts` and a deoplete source, both optional [fetched] https://codeload.github.com/vim-skk/eskk.vim/tar.gz/refs/heads/master . The user dictionary is `~/.skk-jisyo` in UTF-8 by default, the large dictionary is `/usr/local/share/skk/SKK-JISYO.L` in EUC-JP by default, and both take a `sorted` flag and an encoding [fetched] https://raw.githubusercontent.com/vim-skk/eskk.vim/master/doc/eskk.jax .

skk.vim. Repository `vim-skk/skk.vim`, described as skk.vim with miscellaneous hacks [snippet] https://github.com/vim-skk/skk.vim . The help file lists "License: パブリックドメイン", so it is public domain [fetched] https://raw.githubusercontent.com/vim-skk/skk.vim/master/doc/skk.jax . Development is effectively frozen. The latest commit I saw is 2021-08-07 and the last tagged release is v0.27 from 2011-03-10 [fetched] https://github.com/vim-skk/skk.vim/commits/master.atom , [fetched] https://github.com/vim-skk/skk.vim/releases.atom . The whole engine is one `plugin/skk.vim` file plus documentation [fetched] https://codeload.github.com/vim-skk/skk.vim/tar.gz/refs/heads/master . Defaults are `skk_jisyo` at `~/.skk-jisyo` and `skk_large_jisyo` at `/usr/local/share/skk/SKK-JISYO.L`, with encoding guessed unless set [fetched] https://raw.githubusercontent.com/vim-skk/skk.vim/master/plugin/skk.vim .

Neovim Lua plugins. I found four in the 2024 to 2026 window.
`kjuq/skkelua.nvim` is a pure Lua port of skkeleton under the zlib license, created 2026-07-08, latest commit 2026-10-20 [fetched] https://raw.githubusercontent.com/kjuq/skkelua.nvim/master/LICENSE , [snippet] https://github.com/kjuq/skkelua.nvim , [fetched] https://github.com/kjuq/skkelua.nvim/commits/master.atom . It needs Neovim 0.10 or later and no Deno, stores the user dictionary at `$XDG_DATA_HOME/skkelua/jisyo`, and reads SKK, JSON, and msgpack dictionaries [fetched] https://raw.githubusercontent.com/kjuq/skkelua.nvim/master/README.md . Its skkserv support is synchronous with a one second timeout, and it does not ship a ddc source [fetched] https://raw.githubusercontent.com/kjuq/skkelua.nvim/master/README.md .
`nabehan/skk.nvim` is MIT licensed, with v0.1.0 on 2026-08-22 and v0.1.1 on 2026-08-27, and the latest commit I saw is 2026-09-05 [fetched] https://raw.githubusercontent.com/nabehan/skk.nvim/main/LICENSE , [fetched] https://github.com/nabehan/skk.nvim/releases.atom , [fetched] https://github.com/nabehan/skk.nvim/commits/main.atom . It needs Neovim 0.10 or later, has no external process, supports skkserv and blink.cmp integration, and writes the personal dictionary to `~/.local/share/skk/SKK-JISYO.user` by default [fetched] https://raw.githubusercontent.com/nabehan/skk.nvim/main/README.md . Its author wrote that it exists because skkeleton and blink.cmp did not work well together [fetched] https://zenn.dev/nabehan/articles/5df33e5c244e22 .
`takeshy/skk-lite.nvim` is MIT licensed, created 2026-07-31, latest commit 2026-10-15, and needs Neovim 0.10 or later [fetched] https://raw.githubusercontent.com/takeshy/skk-lite.nvim/main/LICENSE , [snippet] https://github.com/takeshy/skk-lite.nvim , [fetched] https://github.com/takeshy/skk-lite.nvim/commits/main.atom . It generates `dictionary.json` from SKK-JISYO files and keeps the user dictionary and learning history in `state.json`, so its data is JSON rather than SKK text [fetched] https://raw.githubusercontent.com/takeshy/skk-lite.nvim/main/README.md .
`noanoano/skk.nvim` has two commits from July 2025 and looks like a stub, so I would not count it as an implementation [fetched] https://github.com/noanoano/skk.nvim .

Vim9 script. `utubo/vim-vim9skk` is MIT licensed and archived, and its README says development stopped in favour of `vim-vim9skkp` [fetched] https://raw.githubusercontent.com/utubo/vim-vim9skk/main/doc/vim9skk.txt , [snippet] https://github.com/utubo/vim-vim9skk . The successor `utubo/vim-vim9skkp` is MIT licensed, calls itself experimental, and had its latest commit on 2026-09-03 [fetched] https://raw.githubusercontent.com/utubo/vim-vim9skkp/main/doc/vim9skkp.txt , [fetched] https://github.com/utubo/vim-vim9skkp/commits/main.atom . It keeps candidates in a popup so the buffer stays clean until confirmation, reads dictionaries through `jisyo` as a list of `path:encoding` entries, and takes a separate `jisyo_user` file plus a recent-conversion file [fetched] https://raw.githubusercontent.com/utubo/vim-vim9skkp/main/doc/vim9skkp.txt . Its README states that breaking changes are frequent [fetched] https://raw.githubusercontent.com/utubo/vim-vim9skkp/main/README.md .

## 4. Calling one shared native engine from an editor

Vim jobs and JSON channels. `job_start()` starts a job without waiting, and `ch_sendexpr()` sends an expression that is encoded by channel type [fetched] https://raw.githubusercontent.com/vim/vim/master/runtime/doc/channel.txt . A channel opened with mode `json` sends messages as JSON, `ch_sendexpr()` accepts a callback for the reply, and the `lsp` and `dap` modes exist as well [fetched] https://raw.githubusercontent.com/vim/vim/master/runtime/doc/channel.txt . vim-lsp is the working example of this shape. It calls `job_start(a:opts['cmd'], l:jobopt)` and then `ch_sendexpr(l:ctx['channel'], l:request, {'callback': ...})` for each request [fetched] https://raw.githubusercontent.com/prabirshrestha/vim-lsp/master/autoload/lsp/client.vim .

Neovim jobs with msgpack-RPC. Neovim "implements the MessagePack-RPC protocol", and `jobstart()` returns a channel id that accepts `vim.rpcnotify()` and `vim.rpcrequest()` when the job was started with the `rpc` option [fetched] https://raw.githubusercontent.com/neovim/neovim/master/runtime/doc/api.txt , [fetched] https://raw.githubusercontent.com/neovim/neovim/master/runtime/doc/vimfn.txt . `vim.rpcrequest()` "blocks until a response is received", so a request per keystroke is a full stop of the editor until the engine replies [fetched] https://raw.githubusercontent.com/neovim/neovim/master/runtime/doc/lua.txt . Neovim's own LSP client uses this shape, starting a server process and talking over stdio [fetched] https://raw.githubusercontent.com/neovim/neovim/master/runtime/doc/lsp.txt . denops is the same architecture, a separate process reached over a channel, which its documentation sells as isolation because "even if a plugin freezes, Vim / Neovim remains unaffected" [fetched] https://vim-denops.github.io/denops-documentation/ .

LuaJIT FFI to a C ABI library. Neovim "should be built with LuaJIT or a compatible fork" and "LuaJIT also comes with useful extensions such as `ffi`" [fetched] https://raw.githubusercontent.com/neovim/neovim/master/runtime/doc/lua.txt . `sqlite.lua` is a real example. It does `local ffi = require "ffi"` and declares `libsqlite3` as its shared library [fetched] https://raw.githubusercontent.com/tami5/sqlite.lua/master/lua/sqlite/defs.lua . This path has no process boundary and no message encoding, but it is Neovim only and needs the library present on each machine.

Vim `libcall()`. The function calls one exported C function in a shared library with a single argument, either a string or an integer, and returns a string, and the help warns it "is NOT a means to call system functions" [fetched] https://raw.githubusercontent.com/vim/vim/master/runtime/doc/builtin.txt . On Unix the plugin library must be compiled position independent [fetched] https://raw.githubusercontent.com/vim/vim/master/runtime/doc/builtin.txt . vimproc.vim is the example. It wraps the calls in `s:libcall`, refuses to run when `has('libcall')` is false, and calls `vp_open`, `vp_kill`, `vp_readdir`, and similar entry points [fetched] https://codeload.github.com/Shougo/vimproc.vim/tar.gz/refs/heads/master . A single string argument means an SKK engine behind `libcall()` would take one encoded request string and return one encoded reply string, so the protocol would be JSON or similar inside that string.

What the sources say about per-keystroke latency. skkeleton sends every mapped key through `denops#request`, and `denops#request` "calls API {method} ... and waits for a result, then returns it", so the editor blocks per key [fetched] https://raw.githubusercontent.com/vim-skk/skkeleton/main/autoload/skkeleton.vim , [fetched] https://raw.githubusercontent.com/vim-denops/denops.vim/main/doc/denops.txt . Issue 43 reports a visible consequence. The mode indicator redraw could lag by one key, because the event fired late when the request returned quickly [fetched] https://github.com/vim-skk/skkeleton/issues/43 . The denops README treats process startup as the known slow part and offers a shared server to avoid it, which is about startup rather than per key [fetched] https://raw.githubusercontent.com/vim-denops/denops.vim/main/README.md . One user's commit message records about 340 ms of blocking on the first insert while loading skkeleton, again a startup cost [snippet] https://github.com/airRnot1106/nvimrc/commit/bfa9d50229da91459b4dfb8dbc65465d23962c3f . I found no published measurement of per-keystroke latency for any of the four mechanisms, including FFI and `libcall`.

## 5. ddskk (Emacs)

ddskk is the reference implementation, described as "a version of SKK ... on GNU Emacs maintained by the skk-dev team" [fetched] https://raw.githubusercontent.com/skk-dev/ddskk/master/README.md . The repository is `skk-dev/ddskk`, not `skk-dict/ddskk`, which returns 404 [fetched] https://api.github.com/repos/skk-dict/ddskk . The license is GPL-3.0 or later [fetched] https://raw.githubusercontent.com/skk-dev/ddskk/master/README.md . The latest release is DDSKK 17.2 "目名 Mena" on 2026-03-29, after 17.1 on 2020-08-15, and the latest commit I saw is 2026-03-29 [fetched] https://github.com/skk-dev/ddskk/releases.atom , [fetched] https://github.com/skk-dev/ddskk/commits/master.atom . Development is slow but present, with candidate filtering work in the March 2026 commits [fetched] https://github.com/skk-dev/ddskk/commits/master.atom . The personal dictionary is `~/.skk-jisyo`, or `jisyo` inside `skk-user-directory` when that is set, saved in the dictionary buffer's coding system, EUC-JIS-2004 by default [fetched] https://raw.githubusercontent.com/skk-dev/ddskk/master/skk-vars.el . skkserv is configured by `skk-server-host` and `skk-server-portnum` [fetched] https://raw.githubusercontent.com/skk-dev/ddskk/master/skk-vars.el . It is the behavior reference the other implementations say they follow, which skkeleton states in its own README [fetched] https://raw.githubusercontent.com/vim-skk/skkeleton/main/README.md .
